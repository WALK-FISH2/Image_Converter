当前网页端和小程序端处理视频的方式一样吗？展示方式一样吗？保存方式一样吗？

15:50

耗时 36秒

不一样。当前三块可以这样理解：

**1. 视频处理方式：不一样**

Web 端是**浏览器前端实时处理**：

- 载入视频到隐藏的 `<video>`
- 每一帧用 canvas 取当前视频画面
- 在浏览器里实时转成字符 / 点阵 / 半调
- 不需要后端
- 本质是“边播放边渲染”

小程序端是**后端预处理**：

- 小程序把视频上传到后端 `/api/process-video`
- 后端用 FFmpeg 抽帧
- 服务端逐帧转成字符 / 点阵 / 半调画面
- 再合成一个新的 MP4
- 小程序下载处理后的 MP4 再展示
- 需要启动后端

所以：**Web 是实时 canvas 渲染，小程序是后端生成成品视频。**

**2. 展示方式：不一样**

Web 端展示的是：

```
原视频 -> canvas 实时处理 -> CRT 屏幕 canvas 显示
```

也就是说，Web 端屏幕里一直是 canvas 在画。

小程序端展示的是：

```
上传前/处理中：canvas 显示缩略图或 demo
处理完成后：<video> 组件播放后端生成的 MP4
```

小程序处理完成后，屏幕区域实际显示的是 `<video>`，不是 canvas。

所以视觉上尽量做成一样，但底层展示方式不同。

**3. 保存方式：不一样**

Web 端保存视频是**录制 canvas**：

- 用 `canvas.captureStream(30)`
- 再用 `MediaRecorder`
- 保存为 `.webm`
- 速度接近视频时长，因为它是在录制播放过程

小程序端保存视频是**保存后端生成好的 MP4**：

- 后端已经生成处理后视频
- 小程序下载这个 MP4
- `wx.saveVideoToPhotosAlbum()` 保存到相册
- 保存时不是重新录制，而是保存成品文件

所以：

| 项目         | Web 端                   | 小程序端                          |
| ------------ | ------------------------ | --------------------------------- |
| 视频处理     | 前端 canvas 实时处理     | 后端 FFmpeg 逐帧处理              |
| 是否需要后端 | 不需要                   | 需要                              |
| 展示         | canvas 动态渲染          | 处理完成后 `<video>` 播放 MP4     |
| 视频保存     | 录制 canvas，导出 WebM   | 保存后端生成的 MP4                |
| 速度         | 保存视频通常接近视频时长 | 处理阶段慢，保存阶段快            |
| 效果一致性   | 浏览器 canvas 字体效果   | 服务端自绘字符/图元，可能略有差异 |

结论：**功能目标一样，但实现方式、展示方式、保存方式都不一样。**

一、修改视频保存方式

目前网页端使用 canvas.captureStream(30) + MediaRecorder 实时录制处理后的视频，存在以下问题：

1. 保存时间基本等于视频时长。
2. 输出分辨率受页面 CRT 显示画布尺寸影响。
3. MediaRecorder 默认编码质量不足，细小字符、点阵、半调和扫描线容易变糊。
4. 保存结果的清晰度低于网页中看到的动态渲染效果。

请将视频保存改为完全在浏览器前端运行的“离线逐帧处理与编码”方式，不使用后端，也不要调用服务器 FFmpeg。

推荐流程：

输入视频
→ 前端解封装
→ WebCodecs VideoDecoder 逐帧解码
→ 在独立的高清导出 Canvas 上执行现有字符/点阵/半调处理
→ WebCodecs VideoEncoder 编码
→ 前端封装为 MP4 或 WebM
→ 下载处理后的视频

具体要求：

1. 不再把 captureStream + MediaRecorder 作为主要保存方案。
2. 不能依靠隐藏 video 按正常速度播放来录制，否则保存时间仍然等于视频时长。
3. 使用 WebCodecs 进行离线解码和编码，处理速度由电脑性能决定。
4. 可以引入适合浏览器使用的轻量级 demux/mux 库。
5. 优先输出 MP4/H.264；浏览器不支持时降级为 WebM/VP9。
6. 使用 VideoEncoder.isConfigSupported() 检查编码支持。
7. 尽可能使用硬件编码，并使用 quality 或 variable bitrate 模式。
8. 保留输入视频的宽高比例，不允许拉伸、压扁或强制裁剪。
9. 导出 Canvas 必须独立于页面 CRT Canvas 的显示尺寸。
10. 不要先从页面显示 Canvas 截图再放大，应按照目标输出分辨率重新渲染每一帧。
11. 输出宽高必须是偶数。
12. 保存的视频应包含当前选择的列数、缩放、对比度、渲染方式、字符集、反相、抖动、辉光和屏幕色调。
13. 视频背景应与图片保存结果一致，保持黑色，不要额外增加绿色背景光。
14. 尽可能保留原视频音频；编码兼容时直接复用音频轨道。
15. 使用 Web Worker 和 OffscreenCanvas（浏览器支持时）避免导出过程中页面卡死。
16. 显示处理进度、当前帧数，并提供取消按钮。
17. 不支持 WebCodecs 的浏览器可以保留 MediaRecorder 作为兼容降级方案，但需要明确提示用户。

小程序端能不能也按照这个逻辑来？只用前端

17:30

耗时 2分钟 55秒

可以做到“只用小程序前端逐帧处理”，但不能直接照搬网页端的 WebCodecs。两端可以采用相同思路，底层 API 不同。

小程序端可采用：

```
本地视频
→ wx.createVideoDecoder(mode: 1) 最快速度逐帧解码
→ 处理 RGBA 帧并渲染字符/点阵/半调
→ WebGL Canvas
→ wx.createMediaRecorder()
→ requestFrame() 主动提交每一帧
→ 导出处理后的 MP4
→ MediaContainer 合并原视频音轨
→ 保存到相册
```

其中：

- [`wx.createVideoDecoder`](https://developers.weixin.qq.com/miniprogram/dev/api/media/video-decoder/wx.createVideoDecoder.html) 能获取逐帧数据，并支持最快速度解码。
- [`wx.createMediaRecorder`](https://developers.weixin.qq.com/miniprogram/dev/api/media/media-recorder/wx.createMediaRecorder.html) 可以录制 WebGL Canvas。
- `MediaRecorder.requestFrame()` 可以主动提交处理后的帧，不必让原视频按正常速度播放。
- `wx.createMediaContainer()` 可用于把处理后的视频轨道与原视频音轨重新组合。

画质和帧率也能让用户选择，因为小程序录制器支持：

- `fps`
- `videoBitsPerSecond`
- `gop`

不过有几个明显限制：

1. 小程序的画面录制器主要支持 WebGL Canvas，现有 2D Canvas 处理代码需要改造。
2. 官方接口码率上限约为 `3000 kbps`，比网页端计划使用的 `12–24 Mbps` 低很多，细小字符的清晰度上限不如网页端。
3. 1080p、60 FPS 对手机性能和内存压力很大，容易掉帧或失败。
4. `VideoDecoder` 和画面录制器必须以真机测试为准，微信开发者工具不一定能完整运行。
5. 长视频会造成明显发热、耗电和内存压力。

因此，小程序前端比较合理的导出档位是：

| 档位 | 建议输出   | 帧率   | 码率      |
| ---- | ---------- | ------ | --------- |
| 快速 | 最高 540p  | 24 FPS | 1200 kbps |
| 高清 | 最高 720p  | 30 FPS | 2500 kbps |
| 精细 | 最高 1080p | 30 FPS | 3000 kbps |

结论是：**可以只用前端，也可以摆脱按视频时长播放录制的方式，但画质、兼容性和稳定性无法达到网页 WebCodecs 或后端 FFmpeg 的水平。** 最稳妥的产品方案是保留后端“高质量导出”，同时增加小程序本地“快速导出”。
