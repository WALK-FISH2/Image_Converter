# IC-84 工程宪章

- Version: 1.0.0
- Ratified: 2026-08-09
- Last amended: 2026-08-09

本宪章规定长期有效的产品和工程原则。它高于实施计划和单次任务，但不能替代具体需求、规格和接口契约。

## 第一条：输出正确性优先

图像和视频必须真正由所选字符、点阵或半调单元重建。不得以普通颜色滤镜、静态封面、单帧截图或界面特效冒充处理结果。

任何视觉优化都不能破坏媒体内容完整性、主体结构、动态连续性和保存能力。

## 第二条：保持媒体比例

从输入解码、低分辨率采样、屏幕预览到最终导出，必须保持输入媒体的显示宽高比。允许使用黑边和编码偶数尺寸，禁止通过非等比拉伸填满容器。

开屏演示允许拥有独立的内部构图适配，但不能改变用户参数含义，也不能泄漏到用户媒体流程。

## 第三条：参数语义跨端一致

Web、小程序和 Server 可以使用不同布局和受设备限制的控件范围，但同名参数必须表达相同含义。API、默认值或枚举变化必须同步更新契约、调用端、测试和文档。

重复实现尚未消除前，每次修改字符集、色调、亮度或几何公式都要核对三个运行端。

## 第四条：真实设备是质量边界

涉及 Canvas 小字号、字体、辉光、透明度、点阵、半调、视频组件、相册权限和网络的改动，不能只依赖桌面浏览器或微信开发者工具。至少使用目标真机验证，并记录设备和结果。

遇到端侧差异时先设计可证伪的诊断，例如字符探针或固定测试图，再调整渲染阈值。

## 第五条：保存结果与预览一致

用户保存的文件必须对应当前媒体和当前参数。视频保存必须得到完整动态视频；图片与视频使用一致的黑色背景基准。任何预览专用装饰不得意外进入文件，除非规格明确要求。

## 第六条：简单、可追踪的架构

优先沿用项目现有原生技术和清晰模块边界。只有在能降低真实复杂度、解决兼容性或提供可验证收益时才引入依赖和抽象。

关键架构决定使用 ADR。需求使用稳定编号，任务和验收条件引用需求编号，不能让关键决定只存在于聊天记录。

## 第七条：配置与用户数据受控

机器 IP、绝对工具路径和部署域名应通过单一配置入口管理。不得提交密钥、`.env`、用户上传媒体、临时帧或生成输出。

公网部署前必须定义媒体保留时间、清理、安全校验、访问控制、资源限制和隐私说明。

## 第八条：完成必须有证据

任务完成意味着实现、适当验证和文档同步全部结束。语法检查只能证明代码可解析，不能证明比例、视觉、视频动态或真机兼容正确。

尚未运行的测试必须明确标为待验证，不能根据推测记为通过。

## 治理

- 修改宪章需要说明原因、受影响需求和迁移方式。
- 删除或弱化“必须”原则属于重大版本变更；新增原则或实质扩大要求属于次版本变更；澄清措辞属于补丁版本变更。
- 与宪章冲突的计划、任务或代码不能通过悄然修改文档获得认可，应先解决冲突或正式修订宪章。
- 每次准备正式发布时审查本宪章、需求基线、需求审计、兼容性矩阵和未完成 P1 任务。
