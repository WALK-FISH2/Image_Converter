# ADR-0001：小程序视频使用后端 FFmpeg 逐帧处理

- Status: Accepted
- Date: 2026-07-12

## Context

微信小程序运行环境无法在所有目标设备上稳定地把用户视频逐帧读取到 Canvas。仅在页面中叠加绿色滤镜不满足“由字符、点阵或半调单元重建视频”的产品要求；把某一帧保存为图片也不满足完整视频保存需求。

## Decision

小程序视频采用服务端处理：

1. 小程序将原视频和当前渲染参数以 multipart 请求上传。
2. Server 使用 FFprobe 读取显示宽高比。
3. FFmpeg 按目标帧率解码为低分辨率 RGB 帧。
4. Node 渲染器逐帧生成字符、点阵或半调画面，背景使用黑色。
5. FFmpeg 编码 H.264 MP4，并尽可能把源音频转为 AAC 后复用。
6. 小程序下载成片，在页面播放并保存到相册。

当前接口使用单个同步 HTTP 请求。输出文件通过临时 URL 提供。

Web 端不强制调用该服务。其原 MediaRecorder 导出决定已由 [ADR-0002](ADR-0002-web-offline-video-export.md) 的浏览器离线 WebCodecs 方案取代。

## Consequences

正面影响：

- 真机不需要本地逐帧视频 API。
- 保存的是完整动态 MP4，而不是预览图。
- 可以统一控制输出编码、比例和背景。

代价与风险：

- 需要运行 Node、FFmpeg 和可被手机访问的服务。
- 处理耗时、上传耗时和服务器资源随视频长度增加。
- 同步请求缺少进度、取消和队列能力。
- 服务器必须管理上传、临时和输出文件生命周期。
- 本地局域网调试与正式小程序合法域名配置不同。

## Alternatives considered

- 小程序本地逐帧 Canvas：目标设备支持不稳定，拒绝作为主路径。
- 仅显示/保存视频封面：不满足动态视频需求，拒绝。
- 给原视频叠加 CSS/组件滤镜：不是真正的栅格重建，拒绝。
- Web 和小程序全部上传后端：可以提高一致性，但增加 Web 使用门槛，暂不采用。
